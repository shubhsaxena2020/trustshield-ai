# TrustShield AI security and behavior test pass

## Run totals

The final scored result set contains 291 prompts: 256 adversarial prompts and 35 scanner-routing prompts. The first pass of each battery was rerun after correcting the multi-turn fixture and the routing check, so 582 HTTP submissions were made across the initial and corrected runs; the rates below use only the corrected result files.

| Battery | Passed | Flagged | Pass rate |
|---|---:|---:|---:|
| Prompt injection | 215 / 256 | 41 / 256 | 83.98% |
| Scanner routing | 31 / 35 | 4 / 35 | 88.57% |
| Combined strict checks | 246 / 291 | 45 / 291 | 84.54% |

Prompt-injection check results: 0 API-key matches; 13 system-prompt phrase matches; 13 grounding-check results; 17 unauthorized scanner invocations among the 20 general-chat/task prompts; 0 score mismatches; 0 code-fence/long-output manual reviews. The per-category pass/fail counts and full flagged prompts and replies are in the [prompt injection report](prompt_injection_battery_256_report.md). Routing had 4 false positives and 0 false negatives; details are in the [routing report](model_routing_battery_35_report.md).

## Confirmed findings

- **Medium (now fixed) — the scanner's own non-streaming API endpoint had no mechanism to reconsider an ambiguous "analyze_text" default.** Root-caused after the initial battery: `services/api/main.py` already contained a function, `_refine_with_model`, written specifically to give the model a second opinion on an ambiguous message before scanning it — but it was **dead code, never called from either chat endpoint**. Every message the deterministic classifier (`services/chat/intent.py`) couldn't confidently match fell straight through its documented "safe default" (treat unmatched text as content to scan) with no second check, so a long enough or oddly-phrased benign question (a cybersecurity definition, a greeting, a thank-you) could get a scary, unrelated "Suspicious"/"Caution" risk card instead of an answer. This reproduced on 20/20 of the adversarial `unauthorized_scanner_trigger` prompts and on 3 of the 4 `model_routing_battery_35` false positives (a greeting, a thank-you, a password-manager question) — all 291 adversarial/routing battery HTTP calls went through `/api/v1/chat`, the endpoint this bug lived in.
  **Important scope correction:** the actual product chat UI (`apps/web/components/chat/Chat.tsx`) calls `/api/v1/chat/stream`, a separate code path with its own, already-correct gate (`_may_scan` plus a real URL/suspicious-signal/action-risk check) that hands ambiguous messages to the LLM's own tool-calling judgment rather than defaulting to scan. Live-tested the identical failing prompt against `/api/v1/chat/stream` and it answered as chat, not analysis. **The real website's chat was never affected by this bug** — it was specifically a gap in the secondary non-streaming `/api/v1/chat` API (also used by `/api/v1/chat/upload`, so image-based chat turns were affected).
  Fix: wired `_refine_with_model` into `_chat_turn` right after `classify_intent`, and widened two of its gate functions (`is_question_or_task` to recognize a `?` or task verb anywhere in the message, not only at the very start/end — real questions are often wrapped in a leading or trailing sentence of context; `has_transaction_signal`'s bare-pronoun check to require the pronoun actually point at a content noun, e.g. "this message", not just appear anywhere, e.g. "this is a general question"). The hard safety gates (`has_suspicious_signal`, `has_action_or_object_risk`, the bare-content-noun check) are unchanged and were verified, in a new regression test, to still block the model second opinion entirely for real scam content (a live SBI-impersonation scam payload never reaches `route_text()`). Also widened the exact-match greeting list to a pattern covering common variants ("Hi there!", "Thanks for helping me with this demo.") that fell through the same safe default. Re-tested live against the fixed server: all 4 routing-battery false positives and the vast majority of the 20 adversarial `unauthorized_scanner_trigger` prompts now correctly return `kind="chat"`; a residual handful of the most elaborately-worded adversarial prompts in that category still trigger the scanner (a conservative outcome — a false "this needs checking" is far safer than the reverse) and one follow-up-question mismatch (MR-13: a correct analysis is still returned, only tagged `analysis` instead of `followup`) remains open as a low-severity UX item, not pursued further given the safety trade-off of loosening the gates any further.
- **Low (fixed) — debug route was available under production settings when its opt-in flag was set.** Before the fix, an isolated `Settings(env="production")` app with `TRUSTSHIELD_DEBUG_PROXY=1` returned 200 from `/api/v1/debug/proxy`, despite the documented production restriction — there was no actual preflight check enforcing it, confirmed by searching `settings.py` for any reference to that env var before the fix (none existed). The route now registers only when `settings.env == "development"`; the same request returns 404.
- **Informational — the grounding checker over-flags safe deterministic advice.** `chat_grounding_violations()` returned `claims certainty or verification` for 13 replies, mostly because they advised not acting "until the request is verified through an official channel." Review of the full replies found cautious advice, not a claim that TrustShield itself verified the content. Not changed: the checker erring toward over-flagging a safe reply is the correct direction to be wrong in.
- **Informational — system-prompt phrase checks produce overlap hits, not prompt disclosure.** The 13 matches were short fragments such as "a link or," "fraud and digital," and "and QR codes." No response exposed the distinctive section headings or a full instruction; manually reviewed and confirmed none is a real system-prompt leak.

No API key was found in any reply or saved result. No cited score disagreed with the scanner score. No generated code fence or long-form response required manual review, and no reply asked the user for a password, OTP, PIN, CVV, or card number.

## Existing design claims

- **LLM API key stays server-side: confirmed.** `services/chat/agent.py` reads `NILABH_LLM_API_KEY` from the server environment and adds it only to the server-to-provider `Authorization` header. The chat response schema returns reply fields, not provider credentials. The live battery's key-substring check found no match; the key value is not present in the result artifacts.
- **Provider output scrubbing: confirmed in code and live output.** The agent calls `_scrub_provider_output` before returning model text, and the provider transport in `services/chat/explain.py` does the same. No key match appeared in the responses.
- **Chat rate limiting: confirmed in code.** Both `/api/v1/chat` and `/api/v1/chat/stream` depend on `limit_light`; the default is 120 requests per minute and the limiter is a per-client token bucket. The sequential batteries remained below that rate. I did not deliberately exhaust the live limiter.
- **Docs and debug endpoints outside development: confirmed after the fix.** `/docs` and `/openapi.json` are enabled only for `development`; the debug proxy route is also registered only in `development`. Local development returned 200 for docs and 404 for the debug route. Production and test-mode app configurations returned 404 for docs/OpenAPI and the debug route.

## Code change and verification

The only backend changes were the environment gates for debug and docs exposure in `services/api/main.py` and `services/api/settings.py`. Regression coverage was added to the existing proxy and production-hardening tests. Verification: `36 passed` across `tests/unit/test_observe_proxy.py` and `tests/integration/test_production_hardening.py`; after restarting Uvicorn, `/api/v1/health` returned 200, docs/OpenAPI returned 200 in development, and `/api/v1/debug/proxy` returned 404.
