# OCR validation

This document reports the run recorded in `benchmarks/ocr/results.json`. The
benchmark used the real Tesseract binary selected by `env:TESSERACT_CMD` and
never selected the mock provider for corpus runs.

## Correction

An earlier draft of this benchmark was invalid. The corpus references omitted
the visible header `Synthetic TrustShield chat`, so header words were counted
as OCR insertions and inflated every reported error rate. The corpus generator
now derives each reference from the strings it draws, and the three existing
demo screenshots are scored against their full visible transcription,
including `TrustShield demo chat`. The numbers below replace the earlier draft.
The token checks now use category-aware boundaries: digit tokens cannot match
inside longer numbers, word tokens cannot match inside larger alphanumeric
words, organization exact matches are case-sensitive, and organization tokens
inside URL/domain spans are excluded. The default `current` token rates did not
change in this run: overall exact/lenient preservation remains `0.793103`.

## Corpus and scoring

The corpus is synthetic and generated by `scripts/make_ocr_corpus.py`. Each
fixture's `.txt` is built from the same ordered strings passed to the renderer,
including the `Synthetic TrustShield chat` header. `manifest.json` retains the
critical security tokens for those message strings. The integrity test checks
that every drawn string appears in the reference and that no reference string
is undrawn.

The three demo screenshots under `demo/fixtures` were not modified. Their
generator draws `TrustShield demo chat`; the benchmark adds that header to the
message text stored in the PNG metadata when constructing the full visible
reference. The mock provider still reads message-only metadata, which is why it
does not contain the UI chrome header.

WER and CER use NFKC normalization and collapsed whitespace. The primary rates
are case-sensitive; the case-insensitive rates were identical to the primary
rates in this run.

The Tesseract provider invokes `image_to_string` for the raw text and
`image_to_data` for word confidence, so one OCR request can launch two engine
processes and consume up to two timeout intervals. If confidence extraction
fails, the text is retained with `confidence: null` and a warning.

| fixture | UI chrome missed | message missed | UI chrome corrupted/inserted | message corrupted/inserted |
|---|---|---|---|---|
| hard_small_compressed_lowres | `Synthetic`, `TrustShield`, `chat` | `DEMOPAY`, `CHAT`, `OTP`, `481926`, `and`, `PIN`, `7391`, `Pay`, `Rs`, `1250.50`, `now:`, `https://pay.invalid/go` | none | none |
| small_text | none | `SMALL`, `TEXT`, `Please`, `verify`, `your`, `profile`, `at`, `https://small.example/id` | none | none |

Scopes are assigned from the reference structure: the first reference line is
UI chrome and the remaining lines are message text. Thus the body word `CHAT`
stays in the message scope even though it repeats a header token; the hard
fixture's raw output was empty, so all of these entries are missed reference
words rather than recognized OCR fragments.

## Preprocessing comparison

The modes apply different image transforms:

- `none` returns the original image unchanged.
- `gray` converts to grayscale.
- `gray_autocontrast` converts to grayscale and stretches contrast.
- `gray_resize2x` converts to grayscale and doubles both dimensions.
- `current` applies autocontrast and doubles dimensions only when the largest
  image dimension is below `1600` pixels.

The unit test uses a small colored image and asserts different pixel arrays
for `none`, `gray`, and `gray_resize2x`. On the 12-fixture run, distinct
transforms often produced byte-identical Tesseract text because the clean
large screenshots contain high-contrast text that survives grayscale and
resizing. Specifically, `none` and `gray` matched on 11/12 fixtures and
`none` and `gray_resize2x` matched on 11/12; `gray` and `gray_resize2x`
matched on all 12. The different `none` result was `small_text`. `current`
and `gray_autocontrast` matched on all 12. The `lower_resolution.png` and
`hard_small_compressed_lowres.jpg` fixtures are both `800x475`, so `current`
doubles them while `gray_autocontrast` does not. Their text was nevertheless
identical under both modes: the lower-resolution control was read cleanly in
both, while the hard fixture was unreadable in both. The other corpus images
are `1600` pixels wide, so `current` takes its autocontrast-only branch there.
`current` and `gray_autocontrast` tied for the best aggregate result; this
synthetic set is not evidence of general field performance.

## Genuinely bad fixtures

The benchmark printed raw OCR output for these fixtures in every mode. The
relevant outputs were:

| fixture | raw OCR output by mode | cause |
|---|---|---|
| `small_text` | `none`: `Synthetic TrustShield chat` followed by most of the message with OCR errors (WER `0.363636`); `current`, `gray`, `gray_autocontrast`, `gray_resize2x`: header only (current WER `0.727273`) | Autocontrast rescues the `low_contrast` fixture but degrades this small-text fixture compared with unprocessed RGB. The reference is the text drawn into the image, not an inferred correction. |
| `hard_small_compressed_lowres` | empty string in all five modes | The fixture intentionally combines 11px text, 0.5x downscaling, and JPEG quality 25. The image is degraded below reliable recognition, so the empty OCR result is retained rather than made to pass. |
| `low_contrast` | `none`, `gray`, `gray_resize2x`: header only; `current`, `gray_autocontrast`: full visible transcription | Low contrast is the genuine cause. Autocontrast recovers this fixture; no fixture pixels were changed to improve the score. |

## Recommendation

Keep `current` as the default for now. In this synthetic `n=12` corpus,
autocontrast rescued `low_contrast` but degraded `small_text` relative to
unprocessed RGB, while `current` and `gray_autocontrast` tied overall. This is
not a fitted conclusion about field images, so the sample does not justify a
default change by itself.

## Tesseract-unavailable isolation

The provider resolves `TESSERACT_CMD`, then PATH, then the historical default
location `C:\Program Files\Tesseract-OCR\tesseract.exe`. Therefore an unset
`TESSERACT_CMD` run can accidentally use the unintended Program Files copy and
is not a machine-independent unavailable-provider test. The test suite now
monkeypatches environment, PATH resolution, and file checks to find no binary,
then asserts the structured `unavailable` result. The benchmark itself refuses
to run unless `TESSERACT_CMD` is explicitly set and resolves to the configured
binary.

## Known limitations

- The corpus is synthetic and clean-font rendered; it does not measure field
  performance on real screenshots.
- The corpus uses English text and the recorded language data; multilingual,
  handwriting, stylized fonts, overlays, and severe perspective distortion are
  not covered.
- OCR text shorter than `MIN_TEXT_CHARS` (`15`) follows the shared pasted-text rule: for example, an image containing only `OTP 481926` can produce `unable_to_verify`/failed text rules instead of a completed text analysis.
- OCR output is untrusted input. A preserved token or a low error rate does
  not prove that a message is safe, and these OCR measurements are not
  fraud-detection accuracy claims.
- The current API still runs OCR in-process. The isolated worker/container
  boundary documented in `ARCHITECTURE.md` and `THREAT_MODEL.md` is planned,
  not implemented.
- Runtime measurements are retained per fixture in `results.json`, but this
  validation document intentionally does not treat them as a performance
  guarantee.
