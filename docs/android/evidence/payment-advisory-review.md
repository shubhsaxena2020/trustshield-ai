# Payment advisory focused review

Scope: static review of the previous-wave diff (`HEAD^..HEAD`, commit `9e24ce7`) against `docs/android/PAYMENT_ADVISORY.md`, the Android lane evidence, and the acceptance checklist. No source/test files changed and no Gradle/JVM/emulator tests were run.

## Findings

- **Documentation is stale/internally inconsistent:** `PAYMENT_ADVISORY.md` says `ResultPresenter` leaves `paymentAdvisory` unset and that no production caller invokes the engine. The reviewed diff adds parser/engine invocation and attaches an advisory in `ResultPresenter.present` when parsed fields qualify. Correct that status and wiring diagram. This establishes Result-presenter wiring, not a demonstrated QR-to-Result path or runtime behavior. The `ResultInput` booleans/count are caller-provided; this diff does not connect `RegisteredPayeeStore` or establish that `payeeMatchesRegistered` was computed against it.
- **Privacy boundary needs precision:** the new presenter processes `input.sourceText` through the payment parser/engine. Source inspection supports transient in-process evaluation, not that OCR output is discarded after parsing or that the entire app never persists/logs it. The review should not imply the advisory is produced only by a screenshot/OCR path: `takeIf { it.isPaymentScreenshot }` controls attachment, while that flag can also arise from parsed payment-like fields. `RegisteredPayeeStore` now rejects display strings outside its mask shape, but its presence still does not establish secure salt provisioning or integration with presenter inputs.
- **Parser negation change:** the added raw-string regex is `Regex("""(?i)(?:\\bnot|\\bnever|\\bno)\\s+$""")`; in a Kotlin raw string those are literal regex escapes (`\b`, `\s`), so the earlier evidence note claiming doubled-backslash defect is incorrect. It only skips a status if an English negation is within the preceding 16-character window and directly separated by whitespace. This is a narrow heuristic, not comprehensive negation/intent analysis; no execution was performed.
- **Scope:** the diff touches payment parser/engine/store, Result presenter/state/card, tests and payment-advisory docs/evidence. These appear feature-related rather than accidental unrelated scope. The added checklist is explicitly unchecked/manual, and tests are assertions, not evidence of passing execution. No scope/privacy issue establishing an unrelated feature change was found in the inspected diff.
- **Potential input-contract concern:** the presenter clamps negative payee counts and clock values, but accepts `payeeMatchesRegistered` independently of the count and does not itself compare a parsed identifier. Ensure upstream callers supply a consistent, locally verified comparison; otherwise the new fields can drive misleading match hints. This diff alone does not prove an exploitable production path.

## Verification limits

This is a source/diff review only. No test/build result, on-device presentation/accessibility, runtime privacy property, or QR-to-Result integration is verified. The payment advisory documentation and any claims of completed acceptance should be reconciled with the new presenter behavior before sign-off.
