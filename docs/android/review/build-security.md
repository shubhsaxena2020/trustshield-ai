## Findings

### BS-01 — The release APK will ship `android.permission.INTERNET` and ML Kit's CCT telemetry backend; the "no INTERNET permission" invariant fails in the merged manifest
Severity: P0
Where: `apps/android/app/src/main/AndroidManifest.xml:1-35`; `apps/android/app/build.gradle.kts:109-110`; transitive `com.google.mlkit:common:18.11.0` → `com.google.android.datatransport:transport-backend-cct:2.3.3`
Scenario: the source manifest declares no INTERNET, and nothing in `main/` opens a socket — so a source-level review, the existing `OfflineContractTest`, and the `_prev` report all pass. But `implementation("com.google.mlkit:text-recognition:16.0.1")` → `com.google.mlkit:common:18.11.0`, whose POM lists `com.google.android.datatransport:transport-backend-cct:2.3.3` at **`scope=compile`** (`common-18.11.0.pom`), and that AAR's manifest (read from the Gradle cache) declares:
`<uses-permission android:name="android.permission.INTERNET"/>`, `<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE"/>`, a `TransportBackendDiscovery` service registered with `backend:com.google.android.datatransport.cct.CctBackendFactory`, plus `JobInfoSchedulerService` and `AlarmManagerSchedulerBroadcastReceiver` from `transport-runtime`. Manifest merger unions `uses-permission`, so **the published APK/AAB requests full network access**, and a Google CCT uploader + its job/alarm scheduling are present at runtime. Any OCR scan can trigger ML Kit event logging. That is exactly the claim the product makes it does not make ("fully offline: no INTERNET permission"), it will show in the Play listing as "full network access", and it silently defeats BS-02's only remaining barrier.
Fix: add `xmlns:tools="http://schemas.android.com/tools"` to `<manifest>` and, next to the CAMERA/RECORD_AUDIO lines:
`<uses-permission android:name="android.permission.INTERNET" tools:node="remove" />`
`<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" tools:node="remove" />` (only after BS-02 removes `networkIsValidated`). If telemetry is to be gone structurally rather than suppressed, also add `configurations.all { exclude(group = "com.google.android.datatransport") }` — but verify OCR still initialises, `MlKitInitProvider` runs at `initOrder=99` and its logging failures must stay swallowed.
Failing test: `app/src/test/java/ai/trustshield/android/BuildContractTest.kt#manifestDeclaresNoInternetPermission` — parse `app/src/main/AndroidManifest.xml` for `<uses-permission android:name="android.permission.INTERNET"` **and** assert `tools:node="remove"` is present; plus a CI step (no Gradle run needed to write it) asserting `grep -L INTERNET app/build/intermediates/merged_manifests/release/AndroidManifest.xml` and `aapt dump permissions` on the release APK.

### BS-02 — Speech auto-switches to the cloud-capable system recogniser whenever the phone is online, with no disclosure and no offline hint actually sent
Severity: P1
Where: `ui/navigation/AppScreens.kt:418`, `:437-451`, `:541-556`, `:593`, `:745-752`; `input/speech/OfflineSpeechEngine.kt:168-190`; `input/speech/CallSpeechSession.kt:527-532`, `:600-606`, `:644-654`
Scenario: `OfflineSpeechPolicy(networkReachable = networkIsValidated(context))` sets `useOffline = !networkReachable`. `networkIsValidated` returns true for any normal phone (INTERNET + VALIDATED capability). So on a real device with wifi/mobile data, `useOffline == false` from first composition, and every mic session is built by `AndroidSpeechRecognizerHandle` → `recognitionModeFor` → `SpeechRecognitionMode.DefaultMayUseNetwork` → `SpeechRecognizer.createSpeechRecognizer(context)`, i.e. the default system recogniser, which on most devices is Google's network recogniser — live call audio leaves the device. Nothing in the consent copy names this: `CallShieldCopy.kt:29` says only "It checks only audio reaching the microphone with your consent", and the "Offline mode: on-device recogniser" banner (`AppScreens.kt:569-580`) is shown *only* when `offlineMode` is already true. Worse, the KDoc at `CallSpeechSession.kt:546-547` claims `buildIntent()` sets `EXTRA_PREFER_OFFLINE`; it does not (`:600-606` sets language model, language, preference, partial results, max results only) — so not even the offline *hint* is sent. Combined with BS-01 the app now also holds INTERNET itself.
Fix: (a) default to `useOffline = true` and treat the platform recogniser as an explicit, labelled opt-in (`speechRoute.selectOffline(false)` only from a button whose copy says audio may go to Google); (b) actually put `putExtra(RecognizerIntent.EXTRA_PREFER_OFFLINE, true)` in `buildIntent()`; (c) fix the `:546-547` doc claim either way. Requires `res/values/strings.xml` copy, no rule-engine change.
Failing test: `CallSpeechSessionTest#platformRouteRequiresExplicitOptIn` — `OfflineSpeechPolicy(networkReachable = true, userSelected = false).useOffline` must be `true`; and `AndroidSpeechRecognizerAdapterTest#buildIntentRequestsOffline` asserting the extra exists on the built intent (extract `buildIntent()` to a pure helper so it is testable without android.jar).

### BS-03 — `assembleRelease` cannot succeed: `ndk.abiFilters` and `splits.abi` are both set, and the ABI set is wrong for the target market
Severity: P1
Where: `apps/android/app/build.gradle.kts:29` and `:32-39`
Scenario: `defaultConfig.ndk { abiFilters += setOf("arm64-v8a","x86_64") }` **and** `splits { abi { isEnable = true; include("arm64-v8a","x86_64"); isUniversalApk = true } }`. AGP rejects that combination at configuration time with `Conflicting configuration : 'arm64-v8a,x86_64' in ndk.abiFilters cannot be present when splits abi filters are set`, so the release build never reaches R8 — the whole minified path (BS-10) is therefore also unexercised. Independently: `armeabi-v7a` is dropped (32-bit low-end Indian phones → `INSTALL_FAILED_NO_MATCHING_ABIS`), and `isUniversalApk = true` ships x86_64 Vosk/JNA/ML Kit natives to every phone. This is unchanged from `_prev` B-04, i.e. still open.
Fix: keep `splits.abi` only, `include("arm64-v8a","armeabi-v7a")`, drop `x86_64` from the release list (keep it in a debug flavour), and delete the `ndk { abiFilters }` block; or drop `splits` entirely and keep `abiFilters`. One of the two, not both.
Failing test: not a unit test — CI job `assembleRelease` must configure and finish; add `unzip -l app-release*.apk | grep 'lib/'` asserting exactly `arm64-v8a` (+`armeabi-v7a`) and no `x86_64`.

### BS-04 — Share intake performs cross-process provider IPC on the UI thread before the first frame (ANR / hostile-provider DoS)
Severity: P1
Where: `MainActivity.kt:76-78` (`onCreate`), `:194-195` (`onNewIntent`), `:221-243`; `input/share/ShareIntentReader.kt:582-591`, `:627-630`
Scenario: `sharedText(intent)` then `sharedImageUri(intent)` each construct `ShareIntentReader(this).read(intent)`, so the intent is read **twice**, and for every stream handle `streamSnapshot` calls `context.contentResolver.getType(uri)` and `declaredBytes` calls `contentResolver.query(uri, [OpenableColumns.SIZE], …)` — two blocking binder calls per URI, up to 5 URIs (`ShareBounds.MAX_IMAGES`), ×2 reads ≈ 20 synchronous cross-process calls inside `onCreate`. A sender sharing `ACTION_SEND_MULTIPLE` with five `content://` handles owned by a provider that sleeps (or a slow cloud provider) gives an ANR on an app the user only tapped "Share" for. Second, independent DoS in the same path: `clipItemCount` is unbounded (`:474-515`) — URI count is capped at 5 but ClipData *text* items are not; thousands of small text items are `toString()`'d, trimmed and de-duplicated into a `LinkedHashSet` synchronously (bounded only by the ~1 MB binder limit) before the first frame.
Fix: read the intent once, off the main thread — move both calls into the existing `LaunchedEffect`/`withContext(Dispatchers.IO)` (`:104-112`) keyed on `entrySequence`, cache the single `ShareIntentRead` and pass it to both the text and image branches; cap `clipItemCount` at e.g. 20 with a `ShareIntentIssue` when trimmed.
Failing test: `MainActivityIntentTest#slowProviderDoesNotBlockOnCreate` (androidTest): a fake resolver/provider that sleeps 10 s; assert `onCreate` returns in <100 ms and the result arrives later; and `ShareIntentReaderTest#clipTextItemsAreCapped` with 50 000 single-char items.

### BS-05 — Vosk model copy is not atomic: an interrupted first copy leaves a permanently broken model, with a native crash on every later session
Severity: P1
Where: `input/speech/OfflineSpeechEngine.kt:108-113`, `:134-143`
Scenario: `VoskDecoderFactory` copies assets only when `File(localModel, "am/final.mdl").isFile` is false (`:112`); `copyAssets` recurses over `assets.list(path)` in the platform's order (alphabetical → `am/` first) and writes files one by one with no temp directory, no completion marker, no size check. A process kill, low storage or a user stopping the session mid-copy (a 42 MB copy on a low-end phone takes seconds) leaves `am/final.mdl` present while `conf/`, `graph/`, `ivector/` are missing or truncated. Every later session then skips the copy, `Model(localModel.absolutePath)` fails inside JNA — producing an uncatchable native abort, not a Kotlin exception — and no code path ever repairs it short of clearing app data. The failure is also silent to the user: `onFailure` just stops the session.
Fix: copy into `model-hi.tmp`, write a `complete.flag` (or verify a file-count/size manifest) last, then `renameTo("model-hi")`; delete the temp dir on any failure; gate on the flag, not on `am/final.mdl`.
Failing test: `OfflineSpeechEngineTest#interruptedCopyIsNotTreatedAsComplete` — a fake `AssetManager` seam that copies only `am/` then throws; assert the next `open()` re-copies and that `Model` is never constructed against a partial directory.

### BS-06 — Release signing config is created unconditionally, with null credentials when `keystore/release.properties` is absent
Severity: P2
Where: `apps/android/app/build.gradle.kts:13-16`, `:41-48`, `:52`
Scenario: with no `keystore/release.properties` (the normal state of a clean checkout, CI, or another dev's machine) `storePassword`/`keyAlias`/`keyPassword` are `null` and `storeFile` points at a non-existent `keystore/trustshield-release.jks`. `signingConfigs.create("release")` still runs and `release` still assigns it, so `assembleRelease` dies with an opaque AGP/NPE message rather than "keystore not configured". No env-var fallback exists for CI. Safety itself is fine (C-8) — no secret is in the repo, and `git check-ignore` confirms `keystore/` is ignored, but note the ignore is only `apps/android/keystore/`: a `.jks` dropped at repo root or in `docs/` is **not** ignored by any rule.
Fix: only `create("release")` when `releaseSigningProperties.getProperty("storePassword") != null`, else leave the release build unsigned and `logger.warn` once; add `root .gitignore` lines `*.jks`, `*.keystore`, `keystore/` (root-level) as a second fence.
Failing test: `BuildContractTest#releaseSigningConfigIsConditional` — parse `app/build.gradle.kts` for a guard around `signingConfigs.create("release")`; plus a CI run of `assembleRelease` without a keystore expecting the explicit warning text, not an NPE.

### BS-07 — `preBuild` depends on a 42 MB network download of the ASR model, wired into every variant
Severity: P2
Where: `apps/android/app/build.gradle.kts:69-97`
Scenario: `tasks.named("preBuild").configure { dependsOn(prepareVoskHindiModel) }` (`:97`) runs for `testDebugUnitTest`, `assembleDebug` and lint too; with `assets/model-hi/am/final.mdl` absent (it is gitignored) and no network, every build fails. `URL(...).openStream()` (`:77-78`) has no connect/read timeout, and `archive.readBytes()` (`:81`) loads the whole 42 MB zip into the Gradle daemon heap (works at `-Xmx2048m`, but it is a needless spike). SHA-256 pinning and the zip-slip guard (`:88`) are correct. `outputs.dir` is declared without matching `inputs`, so the task never re-validates a stale/corrupt model. Build-time only — no runtime network.
Fix: depend on `mergeReleaseAssets`/`packageReleaseAssets` instead of `preBuild`; stream the download to disk with timeouts; verify the digest of `am/final.mdl` as an `input` property so a corrupt model invalidates the task.
Failing test: CI job running `:app:testDebugUnitTest` with networking disabled must pass.

### BS-08 — No data-extraction / backup rules file; `allowBackup="false"` is the single control
Severity: P2
Where: `AndroidManifest.xml:8`; `res/xml/` does not exist
Scenario: today `allowBackup="false"` disables both cloud backup and D2D transfer, so nothing leaks. But `res/xml` has no `data_extraction_rules.xml` or `fullBackupContent`, so the moment anyone flips that attribute (a very plausible "make settings survive reinstall" request) the 42 MB model under `filesDir/model-hi`, both `SharedPreferences` files and the payee HMAC ids become backup-eligible, with no rule to stop it, and lint's `DataExtractionRules` check stays silent. This is the only place in the app where a one-word change converts into a data exfiltration path.
Fix: add `res/xml/data_extraction_rules.xml` with `<cloud-backup><exclude domain="root" path="."/></cloud-backup><device-transfer><exclude domain="root" path="."/></device-transfer>` (exclude `file` and `sharedpref` domains explicitly) and reference it with `android:dataExtractionRules` + `android:fullBackupContent`.
Failing test: `BuildContractTest#backupIsExcludedByRuleToo` — parse the manifest for `allowBackup="false"` **and** for `dataExtractionRules` pointing at an xml whose `cloud-backup` block excludes `sharedpref` and `file`.

### BS-09 — Third-party notices cover only Vosk/JNA; ML Kit ships under its own Terms, and 5 shipped dependency families are unlisted
Severity: P2
Where: `docs/android/THIRD_PARTY.md` (single section, Vosk + JNA + Hindi model)
Scenario: the APK ships ML Kit text-recognition Latin + Devanagari (`com.google.mlkit:text-recognition:16.0.1` license field = **"ML Kit Terms of Service"**, `developers.google.com/ml-kit/terms` — not Apache-2.0, and it carries attribution/usage obligations distinct from Apache), CameraX 1.6.2, ZXing core 3.5.3, Compose/Material3/activity/splashscreen/profileinstaller, and now firebase-components/firebase-encoders + datatransport (BS-01). Failing test: `ThirdPartyNoticesTest#everyImplementationHasANotice` — read `app/build.gradle.kts` `implementation(...)` group ids and assert each appears in `docs/android/THIRD_PARTY.md`.

### BS-10 — The minified release path is never built or tested; no mapping retention, no `-keepattributes` for stack traces
Severity: P2
Where: `apps/android/app/build.gradle.kts:50-56`; `proguard-rules.pro:1-7`; `docs/android/QUALITY_GATES.md:5`
Scenario: `isMinifyEnabled = true` + `isShrinkResources = true` only in `release`, while `buildTypes` defines no `testBuildType = "release"` and the quality gate only requires `assembleDebug` + `testDebugUnitTest` + lint. So R8 has **never** run against this code and no test has ever executed obfuscated classes — a release-only `ClassNotFoundException`/`NoSuchMethodError` would be found on the demo phone. Failing test: CI job `:app:assembleReleaseAndroidTest` + `connectedReleaseAndroidTest` (one Vosk/OCR/QR smoke); gate on the mapping file existing.

### BS-11 — A multi-image share silently analyses only the first image
Severity: P2
Where: `MainActivity.kt:235-243`
Scenario: the manifest advertises `SEND_MULTIPLE` with `image/*` (`AndroidManifest.xml:28-33`), `SharePayloadParser.parseImages` validates and accepts up to 5 images, `ShareIngestCoordinator.ingestImages` is written to analyse all of them under one byte budget — but `sharedImageUri` returns `content.images.firstOrNull()?.uriString` and the rest are dropped with no message. A user sharing a 3-screenshot scam conversation gets a verdict computed from screenshot #1 only, presented as if it covered the share. Wrong-verdict risk, not a crash.
Fix: carry `List<String>` of image URIs into `ImageScanLauncher`/`ShareIngestCoordinator.IngestRequest.Images`, or at minimum surface a limitation line "only the first of N images was checked". `ShareIngestCoordinator` already supports the multi path.
Failing test: `ShareIngestCoordinatorTest#multipleImagesAreAllRead` (pure core, already possible) plus an androidTest `MainActivityIntentTest#sendMultipleAnalysesEveryImage`.

### BS-12 — The share payload stays on the Activity's `Intent` and is re-analysed on every recreation
Severity: P2
Where: `MainActivity.kt:66-95`, `:191-207`, `:212-216`
Scenario: after `onCreate` consumes a share, nothing clears it: `setIntent`/`replaceExtras` is never called, so the raw `EXTRA_TEXT` / `EXTRA_STREAM` / `ClipData` remain on the activity's intent — and are re-read by `onCreate` on every configuration change (rotation) and after process death, where `incomingText != null` forces `entrySequence++` and a second full analysis. Two consequences: (a) a rotation re-runs the pipeline and re-navigates to RESULT, so the user can see the analysis "restart"; (b) raw scanned text lives in the task's Intent for as long as the task does, which is outside the "in memory only for the analysis you asked for" claim and is what a Recents snapshot captures. `onSaveInstanceState` is clean (route + counter only, `:212-216`) — the leak is the Intent, not the Bundle.
Fix: after both reads, `setIntent(Intent(this, MainActivity::class.java))` (or `intent.replaceExtras(Bundle())` + `intent.clipData = null`), and record `consumedEntrySequence` in the saved state so a restore does not re-analyse.
Failing test: `MainActivityResultRetentionTest#rotationDoesNotReanalyseShare` — launch with `EXTRA_TEXT`, rotate, assert the pipeline ran once (fake pipeline counter) and that `activity.intent.getStringExtra(Intent.EXTRA_TEXT) == null` afterwards.

### BS-13 — `EXTRA_ROUTE` is attacker-settable on the exported activity
Severity: P2
Where: `MainActivity.kt:218-219`, `:203-206`; `ui/navigation/AppRoute.kt` (`fromWire`)
Scenario: any installed app can `startActivity(Intent().setComponent(ai.trustshield.android/.MainActivity).putExtra("route","result"))` — the activity is exported for SEND/LAUNCHER, and `routeFromIntent` accepts the extra on both the cold-start and `onNewIntent` paths. The process-death guard (`:87-95`) only fires when an outcome is missing *and* nothing was restored, so a fresh external launch with `route=result` and no outcome navigates to Result with `resultOutcome == null`; `route=call_shield`/`qr_guard` deep-links into a camera/mic screen. No microphone or camera actually opens without a user tap plus runtime permission (verified: `CallShieldHost.onStartRequested` gates on consent+capability+permission), so this is a UI-integrity/phishing-surface issue rather than a capture issue.
Fix: accept `EXTRA_ROUTE` only when `intent.action == Intent.ACTION_MAIN` (or an internal explicit intent with a non-exported companion activity); never route to `RESULT` from outside.
Failing test: androidTest `MainActivityIntentTest#externalRouteExtraIsIgnored` — start with `route=result`, `resultOutcome` null, assert Home is shown.

### BS-14 — `CallSpeechSession(consentGranted = true)` hardcodes away the session's own consent gate
Severity: P2
Where: `ui/navigation/AppScreens.kt:410`; `input/speech/CallSpeechSession.kt:59`, `:119`
Scenario: `CallSpeechSession` refuses to start when `consentGranted` is false (`:119` → `RefusalReason.NO_CONSENT`), and `CallSpeechSessionTest` pins that. The shipping screen constructs it with `consentGranted = true` **before** any consent exists (`SpeechConsent.initial()` is `NotAsked`, created later at `:476`), so that inner gate is permanently open and consent enforcement rests entirely on `CallShieldHost.onCapability` + `ReadinessInput` (`CallShieldReadiness.kt:310`). That gate does hold today (verified), so mic capture is not actually unconsented — but the layer that owns the rule is bypassed in production and the guarantee is one refactor away from being lost, while the test suite keeps proving the dead path.
Fix: pass `consentGranted = false` at `AppScreens.kt:410` and drive it from the real record, e.g. rebuild/`setConsent(consent.canStartSession)` on `CallEvent.GiveConsent`, so `CallSpeechSession` stays the authoritative gate.
Failing test: `CallShieldHostTest#sessionRefusesWithoutConsent` — with `SpeechConsent.initial()` and a granted capability, `onStartRequested()` must not reach `coordinator.prepare`/mic.

### BS-15 — No APK size or ABI gate, and the shipping artifact is far past the documented budget
Severity: P2
Where: `apps/android/app/build.gradle.kts:32-39`; `docs/android/QUALITY_GATES.md:7`
Scenario: the gate says "APK <= 50 MB without optional ASR model, cold start <= 2.5 s, peak PSS <= 250 MB … record measured results", but nothing measures any of it, and the model is no longer optional — it is bundled via `prepareVoskHindiModel`. Arithmetic from the pinned artifacts: 42 MB model + ML Kit Latin and Devanagari bundled models (~20 MB of `text-recognition-bundled-common` jni/assets) + Vosk/JNA natives + Compose ⇒ a universal release APK comfortably over 70 MB, doubled again by `isUniversalApk` shipping both ABIs' natives, with no `androidResources.noCompress` for the `.mdl`/`.fst`/`graph` assets (they compress poorly, so they inflate install size and the first-use `copyAssets` of BS-05). No `unzip -l`/size assertion exists anywhere in CI.
Fix: fix BS-03 (one ABI split, no universal), add `androidResources { noCompress += listOf("mdl","fst","int","dubm","mat","txt") }` for the model dir, and add a CI size/ABI assertion; record the measured numbers in `STATE.md` per the gate.
