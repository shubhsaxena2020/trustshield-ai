## Findings

### CE-01 — Any message wrapped in double quotes is scored with every stage and every evidence item suppressed (a forwarded scam scores 0/`LOW_RISK`)
Severity: P1
Where: `core/rules/LegitimateIndicators.kt:122` (`findQuotedRegions`) → `:350-367`, `:676-682`; consumed unconditionally at `core/score/LocalScorer.kt:435`, `:247`, `:288`
Scenario: `findQuotedRegions` marks **every** `"…"` pair (4–200 chars, `DOUBLE_QUOTED`) and every reported-speech tail as "the sender is quoting", with no requirement that the message also carries protective advice. `LocalScorer.accepted()` then drops any stage item whose span overlaps a quoted region (`:435`), the injection filter drops likewise (`:247`), and the `DigitalArrestSignals` strong signal is filtered the same way (`:288`). Observed: `Fwd: "SBI ALERT: Aapka account 24 ghante mein band ho jayega. Turant 9876543210 par call karein aur OTP batao."` → **score 0 / `LOW_RISK`, `stages = []`, no evidence, limitation "Koi scam pattern nahi mila"**. The identical sentence without the surrounding quotes → **70 / `HIGH_RISK`, `escalateCritical = true`, stages `[THREAT_OR_REWARD, URGENCY, ASK]`**. Also measured: `"Aapka account band ho jayega. Turant OTP batao warna arrest ho jayega."` → 0 / `LOW_RISK`; and a variant with the ask quoted but the threat outside → 24 / `LOW_RISK` (down from 70). Wrapping a message in quotes is ordinary formatting in a forwarded WhatsApp/SMS block (`Fwd: "…"`, `Bank ka message: "…"`), so the engine reports "safe" on the exact scripts it exists to catch. BEHAVIOR_SPEC §"Negation and legitimate pairs" only licenses this for a *quoted scam example inside a legitimate warning*; the grounding condition was never implemented.
Fix: make the suppression conditional instead of global — in `LocalScorer.score()` compute `val quoteSuppresses = assessment.hasProtectiveIndicator` (or require at least one `SECURITY_ADVICE`/`BANK_NEVER_ASKS`/`OFFICIAL_CHANNEL` hit, which is exactly the condition `QUOTED_SCAM_IN_WARNING` already uses at `LegitimateIndicators.kt:161`) and pass it into `accepted()` / the injection and strong-signal filters; when no protective indicator exists, keep the quoted evidence. Second, cap `DOUBLE_QUOTED`/`SINGLE_QUOTED` coverage at, say, 60% of the analysed length so a message cannot quote itself into immunity.
Failing test: `ScorerTest#forwardedQuotedScamIsStillHighRisk` — `LocalScorer(HinglishNormalizer()).analyzeScored("Fwd: \"Aapka account band ho jayega. Turant OTP batao.\"")` must have `verifiedAsk == true`, `risk.score >= 70`, and `unverifiableEvidence(analyzedText)` empty; plus a twin assertion that `"Dhyan dein: \"jo OTP aaya hai batao\" aise message scam hote hain."` stays `< 25` (the case `ScorerTest:213` already pins).

### CE-02 — The ASK stage is evaluated last against one shared evidence budget, so an ask that sits late in a long message is never detected
Severity: P1
Where: `core/rules/StageRules.kt:100-116` (`budget`, `minOf(MAX_EVIDENCE_PER_STAGE, budget)`, `budget -= items.size`), `:63-67` (`MAX_ANALYSIS_CHARS`, `MAX_EVIDENCE_PER_STAGE = 3`, `MAX_EVIDENCE_TOTAL = 12`), `:102` (iteration order = `StageId.playbookOrder`)
Scenario: the loop walks `AUTHORITY → THREAT_OR_REWARD → URGENCY → SECRECY → ASK` and stops (`if (budget <= 0) break`) when the 12-item global budget is exhausted — and ASK is last. A message whose four earlier stages contribute 3 items each consumes the whole budget, so stage 5 is never even run. Observed: `Main SBI se bol raha hoon. Main senior officer hoon. This is HR from Talent Bridge. Aapka account band ho jayega. … Aakhir mein: OTP batao.` → raw hits `AUTHORITY=3, THREAT=3, URGENCY=3, SECRECY=3`, then **`stages = [AUTHORITY, THREAT_OR_REWARD, URGENCY, SECRECY]`, `verifiedAsk = false`, score 56/`SUSPICIOUS`, `escalateCritical = false`** — "OTP batao" is present verbatim and is never read. Prepend the same ask (`OTP batao. Main SBI se …`) and the identical text scores **80 / `HIGH_RISK`, `escalateCritical = true`**. The verdict therefore depends on sentence *order*, which the determinism invariant does not allow and which BEHAVIOR_SPEC's "validated ask + two independent stages ⇒ high-risk floor" forbids.
Fix: give each stage its own budget (`MAX_EVIDENCE_PER_STAGE`, already 3) and drop the shared `MAX_EVIDENCE_TOTAL` from the detection loop — the fusion layer already caps what it reads (`LocalScorer` evidence list). If a global cap must stay, evaluate `StageId.ASK` first (ascending cost), or reserve `MAX_EVIDENCE_PER_STAGE` slots for it.
Failing test: `StageRulesTest#askIsNeverStarvedByASaturatedMessage` — for the input above assert `detection.stages.map { it.stage }.contains(StageId.ASK)` and `detection.askTypes.contains(AskType.OTP_PIN)`; and `ScorerTest#askPositionDoesNotChangeTheVerdict` asserting the same score for the ask-first and ask-last orderings.

### CE-03 — A legitimate family money message reaches `HIGH_RISK` and the full-screen escalation because a completed past-tense transfer is read as a demand
Severity: P1
Where: `core/rules/StageRules.kt:722-724` (money ask patterns using `SEND_MONEY`, `:311-313`), `:623-627` (secrecy pattern 1), `core/rules/DigitalArrestSignals.kt:218-231` (relative + `mat batana` marker), fused at `core/score/LocalScorer.kt:292-337`
Scenario: `Papa ko mat batana, maine 5000 bhej diye hain. Turant check kar lena.` → **70 / `HIGH_RISK`, `confidence HIGH`, `verifiedAsk = true`, `escalateCritical = true`**, evidence `["Turant" (URGENCY), "Papa ko mat" (SECRECY), "5000 bhej" (ASK), "Papa ko mat batana" (digital-arrest STRONG)]` — i.e. a red full-screen alert with haptics on a son telling his family he has sent money. Three separate defects compose: (a) `\b\d{3,}[\d,]*[^.!?\n]{0,40}?\b$SEND_MONEY\b` matches `5000 bhej` even though the verb is a **completed first-person** form (`maine … bhej diye hain`); `SEND_MONEY` has no tense or agent guard, so "I sent" == "send me"; (b) `SECRECY_RULES` pattern 1 fires on `papa ko mat` with no check that the thing being hidden is a *case* rather than a surprise; (c) `DigitalArrestSignals` emits STRONG for `papa ko mat batana`, which is ordinary family speech, and it has no second-person/framing guard (only `digital_arrest` itself sets `requiresSecondPerson`). Because ASK is `MONEY_TRANSFER` (∈ `ESCALATING_ASKS`) with 2 corroborations, fusion releases the critical path.
Fix: add a tense/agent guard to the money-ask family — reject a match when the verb is immediately followed by a perfective (`diye|diya|di hai|diyas? hain|bheja tha|kar diya`) or preceded by a first-person subject (`maine|main ne|hum ne|i sent|i have sent`) within the same clause; and require `SECRECY`'s `mat/na … batana` to co-occur with a threat/authority cue (the `SECRECY_THREAT_FRAMING` set already exists at `:538-541`) before it counts as isolation. Independently, gate the `ghar walon/papa/mummy … mat batana` digital-arrest marker on `SECOND_PERSON` or on an authority/threat stage, as `digital_arrest` already does.
Failing test: `ScorerTest#familyMoneyTransferNoticeIsNotAnAsk` — the input above must have `verifiedAsk == false`, `escalateCritical == false`, `risk.label != HIGH_RISK`; plus a positive twin (`Bhai 2000 bhej do ghar ke liye`) that must still be a verified ask at `CAUTION`.

### CE-04 — The delivery-at-the-door pair from BEHAVIOR_SPEC fails on the everyday phrasing where the OTP digits sit between "OTP" and "agent"
Severity: P1
Where: `core/rules/StageRules.kt:145-149` (`overlapsSkip`, `:243` `SKIP_WINDOW = 24`), `:340-348` (`SKIP_DELIVERY_SHARE_TO_AGENT`), `:698-714` (the OTP ask rule that uses it)
Scenario: `overlapsSkip` tests the `skip` regex only inside `text.substring(start-24, end+24)` of the *ask* match, but the skip pattern's own forward reach is `(?:share|give|hand over)\b[…]{0,24}?(?:delivery\s+)?otp\b[…]{0,32}?\b(?:agent|courier)\b` — far more than 24 chars past the ask. So the guard is silently clipped whenever the natural wording is a little longer. Observed: `Delivery OTP 8891. Share only with agent at your door.` → 0 / `LOW_RISK`, no ask (guard works). `Please share the OTP with the delivery agent at your door.` → 0, no ask (guard works). **`Your Amazon order will be delivered today. Share the delivery OTP 4471 with the delivery agent at your door.` → 30 / `CAUTION`, `verifiedAsk = true`**, evidence `["Share the delivery OTP" (ASK, HIGH/STRONG), "delivery agent" (legit_indicators)]` — the app shows a *"code maanga gaya"* card and a green *"Delivery OTP darwaze par dene ke liye"* card in the same result, and a `CAUTION` verdict, on the single most common legitimate delivery SMS. The skip match ends one character past the 24-char halo, which is why the third phrasing (with `4471`) fails and the first two pass.
Fix: make the halo proportional to the pattern instead of a constant — `overlapsSkip` should test the skip regex on `text.substring(from, min(text.length, end + SKIP_FORWARD))` with `SKIP_FORWARD = 72` (the pattern's own worst-case reach) or, better, apply `skip` to the whole clause (`[^.!?\n]`-bounded) rather than a window. Keep the window start at `start - SKIP_WINDOW`.
Failing test: `StageRulesTest#deliveryAtDoorWithOrderDigitsIsNotAnAsk` — the Amazon sentence above must produce no `StageId.ASK` and `askTypes` empty; `ScorerTest#twin pair delivery at door versus remote otp request` should be extended with this third phrasing asserting `< 25`.

### CE-05 — A routine LPG/courier cash-on-delivery notice is promoted to a verified personal-data/callback ask, which the rule's own KDoc says must not happen
Severity: P2
Where: `core/rules/UtilityServiceRules.kt:260-297` (`Personal number par call karne ko kaha`), `:197-207` (`HIGH_STAKES_OR_BANK_CALLBACK_CONTEXT` incl. `pay\w*|payment`)
Scenario: `Dear customer, your LPG cylinder will be delivered today. Payment Rs 950 on delivery. Call 9876543210 for delivery status.` → **30 / `CAUTION`, `verifiedAsk = true`**, evidence `["Call 9876543210" (ASK, STRONG, `AskType.CALLBACK`)]`. `requires` is satisfied by the word "Payment", and pattern 3 (`\b(?:call|phone|dial|contact)\s+(?:on|at|to|this|the)?<mobile>`) matches the delivery-status number. The KDoc at `:190-195` states the opposite outcome for exactly this message class ("a courier or LPG message that merely gives the delivery agent's own mobile … must stay in the watch band"), and `HardeningRegressionTest#an lpg delivery notice raises no ask` covers a different wording. Consequence: the UI prints `ACTION_CAUTION_ASK` ("Is message mein code ya paise maange gaye hain") on a legitimate utility notice.
Fix: move `pay\w*|payment` out of `HIGH_STAKES_CALLBACK_CONTEXT` (a cash-on-delivery line always says "payment"), and require the high-stakes word to be inside the same clause as the callback imperative rather than anywhere in the message.
Failing test: `HardeningRegressionTest#cashOnDeliveryNoticeWithPaymentWordRaisesNoAsk` — assert `verifiedAsk == false` and `StageId.ASK !in result.stages` for the sentence above.

### CE-06 — A legitimate "pay the clearance fee to the courier" notice reaches `HIGH_RISK` + `escalateCritical`, because the customs-clearance ask rule never requires an unofficial channel
Severity: P2
Where: `core/rules/ScamOfferRules.kt:530-558` (`Parcel customs mein ruka - clearance fee`; `requires = OFFER_PARCEL_FRAME` at `:557`), combined with the bare `customs` authority noun at `core/rules/StageRules.kt:389-393`
Scenario: `Your parcel has been held at customs. Pay Rs 250 clearance fee at the counter when the courier arrives.` → **70 / `HIGH_RISK`, `confidence HIGH`, `verifiedAsk = true`, `escalateCritical = true`**, evidence `["customs" (AUTHORITY), "parcel has been held" (THREAT), "Pay Rs 250" + "Pay Rs 250 clearance fee" (ASK, MONEY_TRANSFER)]`. The rule's KDoc (`:531-534`) justifies itself with "asli customs duty parcel deliver karte waqt official channel se leta hai, message par UPI se nahi", but the pattern needs only a fee noun plus any `OFFER_PAY_VERB` inside a parcel frame — no link, no UPI, no personal number. Paying customs duty at the door is normal, and the app answers with the full-screen red path.
Fix: add `UNOFFICIAL_LINK` or `INDIAN_PERSONAL_MOBILE`/`upi|gpay|phonepe|paytm|scan` to this rule's `requires` (the parcel-link rule at `:559-594` already shows the shape), so an over-the-counter instruction cannot become a strong ask.
Failing test: `ScorerTest#customsDutyAtTheCounterIsNotACriticalAsk` — assert `escalateCritical == false` and `risk.label != HIGH_RISK`; keep a positive fixture that pays "via this link / on UPI" at `>= 70`.

### CE-07 — Digital-arrest markers fire on ordinary family speech: a legitimate "stay in your room, don't tell the family" message becomes `CAUTION`
Severity: P2
Where: `core/rules/DigitalArrestSignals.kt:232-242` (`kamre mein akele raho`), `:218-231` (`ghar walon/papa/mummy … mat batana`), `:82-123` (`detect`, second-person guard only for `digital_arrest_named`)
Scenario: `Beta kamre mein akele raho aur aaram karo. Turant dawai le lo. Ghar walon ko mat batana, warna wo pareshan ho jayenge.` → **37 / `CAUTION`, `stages = [URGENCY, SECRECY]`**, evidence `["Turant", "Ghar walon ko mat", "akele raho", "Ghar walon ko mat batana" (STRONG), "kamre mein akele raho" (STRONG)]`. Two STRONG items put `WEIGHT_STRONG_SIGNAL = 20` into the no-ask noisy-OR and, with 2 other stages, `noAskBand` lifts the result into the 25–49 caution band. The `ADVISORY_CUE` guard does not apply (no "beware/news"), and `requiresSecondPerson` is false for these two markers, so a parent's instruction is indistinguishable from an isolation order.

### CE-08 — A bare shortener/throwaway link is never surfaced as evidence on the readable path, contradicting BEHAVIOR_SPEC
Severity: P2
Where: `core/score/LocalScorer.kt:270` (the only call site of `urlEvidence`) and `:462-481`
Scenario: `urlEvidence()` is invoked **only** from the `unableToVerify` branch (`:270`). On the normal, readable path a link becomes evidence only if a KYC/parcel rule happens to match. Observed: `Dear customer, your refund of Rs 4,500 is ready. Click https://bit.ly/3xYz to claim now.` → **0 / `LOW_RISK`, `confidence MEDIUM`, `evidence = []`**, limitation "Koi scam pattern nahi mila" — no link card at all. BEHAVIOR_SPEC §"Deterministic Android behavior" and the class KDoc (`:128-129`) both promise that "a static link that is still attributable is kept as an informational evidence item", and report §3.3 classes a shortener as Weak-to-Moderate; here the user gets a clean result and no indication that the message is built around a shortened link.
Fix: call `urlEvidence(analyzed)` in the readable path too and append it to `evidence` as `INFORMATIONAL`/`WEAK` (it carries no stage, so it cannot move the score unless a deliberate `WEIGHT_URL` is added; the link is still never opened).
Failing test: `ScorerTest#shortenerLinkIsAlwaysReportedAsInformationalEvidence` — the sentence above must produce one `module == "local_fusion"` / `Severity.INFORMATIONAL` item whose quote is `https://bit.ly/3xYz`, and `risk.label` must stay `LOW_RISK` unless the score change is intended.

### CE-09 — `DevanagariRules`' design note states a false fact about the engine it was written around (danda clause splitting)
Severity: P2
Where: `core/rules/DevanagariRules.kt:77-78` vs `core/rules/StageRules.kt:244`
Scenario: the KDoc says "`StageRules` splits clauses on `.` `!` `?` `;` `,` and newlines but not on the danda `।`, so a negation on one side of a danda can still scope across it. Nothing here depends on that." `CLAUSE_BREAKS` in `StageRules` **does** include `'\u0964'` (the danda, `:244`), and so does `isClauseSeparator` in `LegitimateIndicators.kt:322-323`, so the stated cross-danda negation leak does not exist and the note misleads the next author into adding a redundant guard. (Note the `,` difference is real: `StageRules` treats `,` as a clause break while every Devanagari pattern excludes only `। . ! ?` inside a sentence — mixed punctuation can therefore split an ask's span in the Roman rules and not in the Devanagari ones.)
Fix: delete the danda sentence, and state the `,` asymmetry instead (or add `,` to the Devanagari patterns' character class if the parity is wanted).
Failing test: doc-only — no test; verified by `StageRules.CLAUSE_BREAKS` containing `'\u0964'` at `:244`.

## Verified clean (re-checked by execution, not assumed)
- **C-1 Determinism.** Same input → byte-equal `ScoredResult` and equal `analysisId` across runs (3 inputs incl. leet/emoji/Devanagari); `analysisId` is an FNV-1a hash of the analysed text plus input type and sensitivity (`LocalScorer.kt:650-658`) — no clock, counter or random.
- **C-2 Quote/span invariant.** `unverifiableEvidence(analyzedText)` was empty in every sample, and `input.substring(span.start, span.end) == quote` held for every item; `StageRules.toEvidence` takes the quote from `rawQuoteOf` (raw spans) and drops any item `Evidence.verified` cannot locate (`StageRules.kt:210-224`).
- **C-3 Span map vs zero-width / leet / expanded glyphs.** `OTP\u200B batao` still yields the ASK with a verbatim raw quote (zero-width kept inside the quoted span), `b1jli`, `k🔥y🔥c`, `ओटीपी बताओ` and a decomposed Devanagari ask all detect; `matchUnitRun`/`matchLeet`/`matchSpacedToken` are whitelist-gated, so ordinary words are untouched (`optional`, `total`, `stop`; `a b c`, two-letter runs).
- **C-4 Locale.** No locale-sensitive case operation on the decision path: `Character.toLowerCase` and `Char.lowercaseChar()` (index-preserving) in the normalizer and `StageRules.lower()`; `String.lowercase()` where used is Kotlin's `Locale.ROOT`. Turkish dotless-i cannot change a verdict.
- **C-5 Backtracking.** Every quantifier in `StageRules`, `LegitimateIndicators`, `UpiPaymentRules`, `UtilityServiceRules`, `ScamOfferRules` and `DigitalArrestSignals` is bounded; `skip` regexes run against `match ± 24` substrings and `CoreModel`'s `URL_PATTERN` is a linear `[^\s<>"']{3,}`. No catastrophic case found in 20 000-char probes.
- **C-6 Thread-safety.** The only mutable state is `LegitimateIndicators.lastAssessment`; every internal call site passes the explicit `assessment` (`LocalScorer.kt:247/288/310/435` use `LegitAssessment.isQuoted`/`reduce(…, assessment)`), so a shared `LocalScorer` is not internally racy — the footgun is limited to the public no-arg `LegitimateIndicators.isNegated/reduce/currentRiskReduction` overloads, which the KDoc already flags.
- **C-7 `Redactor`** (spot-checked by execution): `OTP 482913` → `OTP [REDACTED]`, `4111 1111 1111 1111` → `[REDACTED]`, `9876543210` → `[REDACTED]`, `account no 123456789012` → `[REDACTED]`, `ramesh@okhdfcbank` → `[REDACTED]`, and `Your order 1234 of Rs 500` left untouched (no over-masking). `MASK` contains no digits/`@`, so the pass is idempotent as documented.
- **C-8 20 000-char bound.** `LocalScanPipeline.analyzeText` does not pre-truncate (A05 owns it), `inputTruncated` is true, `LIMIT_TRUNCATED` is added and confidence caps at `MEDIUM`; `sanitizeInput` caps at exactly 20 000 without splitting a surrogate pair.
- **C-9 Stage/ask independence.** Repeated identical lines collapse (`accepted()` dedupes on `normalizeKey`), a stage counts once by id, and `"OTP batao"` × 5 stays `[ASK]` at `30 / CAUTION` — the documented "ask alone never accuses" rule holds.

## Unverified suspicions
- **NFC/NFD composition.** `foldGlyphs` applies NFKC **per code point** (`HinglishNormalizer.kt:162-183`), which cannot compose a base + combining mark pair. A canonically *decomposed* spelling of a Devanagari word whose rule pattern uses the precomposed form could therefore miss. I did not find a real failing pair, so this stays unverified.
- **`Evidence.locate` picks the first occurrence** (`Evidence.kt:154-158`), so when a quote repeats, the stored span points at the earlier occurrence while the match was the later one. The quote still verifies verbatim (invariant intact); only the highlighted region can be the wrong one. Not demonstrated as user-visible.
- **`ScanOutcome.analyzedText` vs the analysed window.** With input > 20 000 chars, `ScanOutcome.analyzedText` is the full trimmed string (20 005 in my probe) while only the first 20 000 were analysed — the KDoc at `LocalScanPipeline.kt:22-23` says `analyzedText` is what the verdict was produced from. Harmless today (quotes cannot come from the tail) but the contract text is wrong.
- **`HIGH_STAKES_OR_BANK_CALLBACK_CONTEXT` re-compiles an already-expanded pattern** through `rx()` (`UtilityServiceRules.kt:205-207`). Reading it, the transformation is idempotent (`\b` has already been replaced); the LPG probe fired as expected, so I found no defect — recording it only because a future `rx()` change could double-expand it.
- **Ask-first vs ask-last independence in call mode.** `CallSessionState` persists ASK evidence and `LocalScorer` counts `persisted` stages into `present`, so CE-02's starvation can be masked (or not) differently in a call than in a one-shot text scan. I verified the text path only.
